# 苹果与梨：接入真实图像转 3D

用户提供苹果与梨的新素描，反馈原结果不合适，并要求继续优化或加入 2D 转 3D 模型。
本次本机复现中，旧视觉模型能正确认出两种水果，约 7.666 秒返回定位；问题在形状：
苹果与橙子共用简化轮廓，苹果凹槽没有建出、果梗大部分埋入顶部，梨肩变得过尖。
因此“识别成功／网格合法”不能当作形似验收。

## 实现与分工

- Step3-VL-10B Q4_K_M 继续识别对象类别。纯水果素描只需类别和有边界的区域框，
  不再依赖果梗／梨颈框，也不再把这些框转换成旋转曲面。
  若回复 JSON 缺少闭合括号，或混合静物遗漏必要水果部位，最多补充识别一次；
  两者共用同一个重试额度。未知对象、越界坐标和 3D 模型失败不因此重试。
- 全部主体为苹果、梨或橙子时，一张原图交给已经安装的本地 U2Net + TripoSG，
  一次生成整组无贴图网格。头像与水果共享原来的 `mesh.portrait` 插槽及单作业限制，
  没有另加一份模型权重、生产依赖或云端调用。
- 方体、球体、直立圆柱，以及它们与水果混合的静物，继续走现有 CPU 拟合路径。
  头像与独立静物混合仍不支持。最多六个主体，识别中的未知对象不会被删掉凑出场景。
- 水果表面采用 80 次有界 Taubin 平滑，头像仍为 8 次。测试发现的圈状起伏在关闭
  阴影后仍存在，来自网格，不是光照方向；平滑减少起伏但没有消除所有细节误差。
  最大顶点位移仍限制在 0.06 世界单位，过度位移与碎裂表面继续拒绝。
- 浏览器保留原图宽高比，提供原画对照、透视旋转和可移动点光源。调灯不调用模型，
  相机转动复用阴影贴图。水果服务未就绪有单独提示，失败不自动换成简化球体。

TripoSG 是专用图像转网格模型，通用视觉语言模型承担识别；两者职责不同。
上游介绍及固定源码参见 [TripoSG 官方仓库](https://github.com/VAST-AI-Research/TripoSG)。
安装、固定版本及唯一运行入口仍在 [本地重建运行说明](../../studio/portrait_runtime/README.md)。

## 真实验证

原图为用户提供的 1536×1024 私有苹果与梨素描；只发往本机回环服务。
独立调用 TripoSG（MPS FP32、20 步、原来的 8 次平滑）约 63.721 秒、59,994 三角形，
用于与旧曲面做首次对比。苹果凹槽、两个果梗和梨的肩部均比旧版完整。
随后同一原图经课堂上传预处理、80 次水果平滑，完成整个 7070 课堂流程：

| 范围 | 实测 |
|---|---:|
| 安全筛查 | 23.053 秒 |
| 识别 + 去背景 + 3D 生成与处理 | 69.236 秒 |
| 完整后端阶段合计 | 92.289 秒 |
| 同一课堂作品再次生成 | 0.005 秒、0 token |
| 最终课堂网格 | 59,990 三角形 |

加载最终识别指令及格式恢复代码后，再次从完整课堂上传同一原图：安全 8.716 秒，
识别与生成 70.965 秒，合计 **79.681 秒**，成功进入交互查看器。两次安全耗时不同，
所以完整等待约 80–92 秒，不能把差异全部归因于 3D 性能优化。

这些计时口径不同；第一次 63.721 秒不包含课堂安全检查，0.005 秒不包含浏览器显示。
本机有其他服务运行，不是隔离硬件基准。原图、实际模型输出和课堂网格保存在忽略的
`scratch/relight/`，不在本报告或 Git 中保存用户素材。

真实页面检查了原画并排、灯从左移到右并升高后的表面明暗与投影、10° 视角旋转、
复位、再次生成缓存，浏览器无脚本错误。当前结果仍有表面起伏，背面和两个水果
接触处为模型估计，不是精确扫描或可以逐个编辑的独立水果模型。

识别回归曾暴露两种失败：胸像底座被拆成圆柱、几何体 JSON 缺少最终闭合括号。
前者收紧头像及附属底座的指令，后者增加上述有上限的格式重查；没有猜测并补造坐标。
最终真实看图检查中，三几何体走 `geometric-approximation`，头像走头像分流，
球体／方体／梨仍走 `parametric-still-life`。本次头像只重测视觉分类和路由，
路由检查的网格为测试替身，没有再次运行耗时的头像模型，不能当作新增头像质量验收。

## 程序检查与资源边界

- 完整普通后端 **714 passed、8 deselected**，完整前端 **106 passed**，构建结构检查通过。
  数量包含共享工作区其他任务，不是本次新增数量。
- 隔离网格环境另跑 **3 项**真实网格处理检查：水果采样起伏减少、碎裂拒绝、
  过度平滑位移拒绝。球面用径向法线作为参照，避免把真实曲率算作噪声；旧 8 次
  平滑的对照确实使水果质量检查失败。普通课堂环境没有安装 numpy / trimesh。
- 路由检查覆盖纯水果、混合几何、原头像、无效区域与未知对象、安全拒绝、
  失联／忙碌／生成拒绝、缓存、HTTP 单作业和不接受浏览器 Origin。
  测试中的假模型只证明流程；真实模型的形似与耗时见上文。
- 沿用长边 1024 输入、20 步、2048 潜在 token、128³ 采样场、4096 查询块、
  单 GPU 作业、6 万顶点／6 万三角形／8 MiB 出口。平滑在 CPU 执行，不提高 GPU
  解码分辨率。仍使用 100 万像素画布上限、六面 1024² 阴影图及按需绘制。
- Spark 中复用原来的 20 GB 重建规划预留，不增加另一份常驻模型。官方列出
  128 GB 统一内存、273 GB/s 带宽，不能据此推出生成时间；见
  [NVIDIA 硬件说明](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)。
  当前 CUDA 分配器限制仍为 12 GiB，它不包含 CPU 和非 PyTorch 分配。

本次真实生成只验收这组苹果与梨；橙子、任意水果和真实学生画的泛化未验收。
原有 98% 主连通表面门槛保持不变，明显分开的物体可能被拒绝。
DGX Spark / ARM64 / GB10 的实际运行峰值、延迟和真实平板帧率尚未实测。
