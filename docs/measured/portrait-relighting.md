# 头像素描重建与交互调光

用户要求把头像也纳入素描的立体光影功能。原路径只拟合方体、球体和直立圆柱，
因此截图中的石膏头像被拒绝，并非模型已生成头像后渲染失败。
现已增加单个头像／石膏胸像的本地 TripoSG 路径，并完成截图同款原图的真实课堂闭环。

## 实现与模型分工

- Step3-VL-10B 只判定是头像还是可拟合的基础几何，并定位基础几何；不生成头像网格。
- 单个头像（含颈肩、底座）经过本地 U2Net 去背景，再由 TripoSG 生成无贴图三角网格。
  源码固定为 `fc5c40990181e2a756c4e0b1c2f4d6b5202faf8c`，权重固定为
  `2c1c516d22d58db486a058d98d31bb6177344e06`。上游来源：
  [TripoSG](https://github.com/VAST-AI-Research/TripoSG)、
  [模型仓库](https://huggingface.co/VAST-AI/TripoSG)。
- 浏览器 WebGL 负责透视、转动、点光源明暗和立方体阴影贴图。移动灯和相机不调用模型；
  原画的旧阴影没有烘焙到网格表面。可导出当前视角和光照的 PNG。
- 同一课堂作品的成功结果保存在会话缓存；刷新／结束课堂不承诺持久恢复。
  缺失工作进程、输入不支持、无效网格分别处理；不会用预制头像冒充原画重建。

配置、安装与启动的唯一操作入口为 [portrait_runtime/README.md](../../studio/portrait_runtime/README.md)。
重型依赖隔离在 Python 3.11 环境，普通课堂环境不加载 PyTorch。当前本机安装位于忽略的
`scratch/portrait/`，模型服务监听回环地址 7240；这不是 Spark 部署。

## 真实样本与时间

本机 Apple Metal，PyTorch 2.6.0、diffusers 0.32.2、transformers 4.46.3。
用了私有目录中的两张头像素描：`06-head-excellent.png`（截图同款切面石膏头像）和
`05-head-basic.png`。原图、网格和诊断截图不纳入公开报告或 Git。

| 真实运行 | 结果与范围 |
|---|---|
| Step3 头像分类 | 两张分别约 4.17 / 3.83 秒；输出头像路由，不生成形体 |
| TripoSG FP32，20 步 | 两张约 63.16 / 69.36 秒，包含去背景和模型网格生成；不含课堂安全筛查 |
| 截图头像完整课堂，第 1 次 | 安全 42.953 秒 + 重建 81.450 秒，约 124 秒 |
| 截图头像完整课堂，第 2 次 | 安全 24.760 秒 + 重建 73.954 秒，约 99 秒 |
| 同一课堂头像再次生成 | 缓存阶段 0.004 秒、0 token；未重新生成网格，不包含浏览器显示时间 |

课堂计时来自真实服务阶段记录，非单元测试；两次完整调用均通过。本机还有其他服务运行，
不是隔离硬件基准。测试用专用 7070 课堂把视觉与安全都接到本地 Step3，本次没有向云端
发送素描。常规 `local` 配置的其他插槽仍各自选择服务商，不能据此宣称整个产品全离线。

两个头像均生成了可辨识的头、五官、颈肩和底座，清理后约 3 万顶点、6 万三角形。
浏览器真实检查了原图并排、旋转视角，以及灯从左移右时脸部明暗、鼻子阴影和地面投影改变。
短窗口控件原来被父容器压缩裁掉，现可滚动访问完整控件。
真实 WebGL 使用课堂返回的网格导出 810×810 PNG，172,203 字节，文件头和浏览器解码通过，
并检查了画面内容。课堂导出按钮没有浏览器脚本错误，但内置浏览器的自动化下载事件超时；
因此确认的是 PNG 数据生成，未确认下载文件已落到用户的下载目录。

## 被淘汰的速度路线

- TripoSR 生成网格只需约 1–2 秒，但同一头像的额头、脸颊和轮廓明显失真，因此没有接入。
- TripoSG 在本机 MPS FP16 下约 35–43 秒，但出现多片碎裂表面；固定初始噪声、改用 FP32
  解码仍未修复，不能用仅节省时间的结果交付。
- MPS FP32 30 步约 111 秒，20 步在两个样本上保持完整主体，采用 20 步。
  这项精度结论只适用于本次 MPS 环境，不能推导 CUDA FP16 一定失败。

细节仍有体素阶梯感。表面处理只移除很小的数值碎片、减面并做有位移上限的平滑；
若最大主体不足总面积的 98%、网格越界或不稳定，仍拒绝结果。实际坏 FP16 网格作为
负例被拒绝，两张 FP32 网格作为正例通过。不能把这些检查当作五官相似度验收。

## DGX Spark 的边界

- 重建串行，一个 GPU 作业；输入长边 1024、20 步、2048 潜在 token、128³ 采样场、
  解码每块 4096 查询点。没有每次生成时的下载或云端网格回退。
- 出口上限 6 万顶点／6 万三角形／8 MiB。CUDA 采用上游 FP16 路径，PyTorch 分配器设
  12 GiB 上限；该限制不包括 CPU 与非 PyTorch 分配，不能当作整进程峰值。
- `spark.yaml` 为头像预留 20 GB 规划额度，包含加载和去背景；当前配置常驻 68 GB +
  轮换 19 GB = 87 GB，接近 90 GB 课堂上限。这只是配置检查，不是硬件压力测试。
- 浏览器按需绘制，最多 100 万像素，阴影六面各 1024²（颜色存储 24 MiB，另有深度和网格）。
  相机旋转复用阴影贴图；光源变化才更新六面；关闭释放资源。渲染发生在使用页面的设备上。
- 尚未有 Spark 实机，未测 GB10 / ARM64 的运行环境、CUDA 算子、整机同时驻留峰值、
  连续多图性能和真实平板帧率。不能承诺两秒生成或把本机计时当作 Spark 性能。

## 验证层次与限制

网格边界、提供者只连回环、响应大小限制、并发拒绝、安全拒绝、缺失工作进程、头像路由和缓存
由 Python 测试覆盖；矩阵、几何、阴影更新次数和资源释放由 JavaScript 测试覆盖。
这些测试中的假模型和假 WebGL 只证明控制流程；真实模型与真实浏览器证据单列在上文。

最终专项后端 122 项通过（头像、几何体、课堂、媒体插槽、day-zero、HTTP 服务），相关页面
47 项通过（网格、调光、导出、双语、状态）。上游可选 `diso` 补丁在固定版本原文件上
通过 dry-run。没有重装或修改普通课堂的生产依赖。

共享工作区的全量后端检查为 655 passed、6 failed、8 deselected：5 项模型板测试仍假定
`local.vlm.studio` 是本地 Step3，1 项评测来源测试仍断言 Step3；并行任务已将该插槽改为
在线 Qwen。本次保留该配置，没有改写这些检查来获得绿色结果。全量页面检查在另一个
并行修改中的 `navigation.test.mjs` 挂起，停止了本轮的测试进程，未触碰另一任务的进程。
这两项全量结果不能报告为全部通过。

这次支持单个头像和胸像，不含多人物、全身、任意雕塑。单幅图的背面和遮挡面由模型估计，
初始视角未精确匹配原图，五官及笔触不会完全还原。仍需更多真实学生画验证泛化。
首次完整等待仍约 1.5–2 分钟，速度问题没有消失；缓存后的再次打开和灯光交互不再生成网格。
