# Contributing to 画里画外 Beyond Canvas

Thank you for helping. Beyond Canvas works with children's drawings and a child's own words, so a few
rules come before any code.

## Children first

- **Never commit a real child's drawing, photo, voice, name or class data.** The evaluation drawings in
  `skills/*/evals/files/` are generated by programs or image models; keep it that way. The studio's own
  state in `.studio/` (course portfolios, ledgers, logs) and your keys in `.env` never go in a commit.
- **Every drawing passes `studio-safety` before any other Skill sees it**, and every picture or clip the
  studio makes is screened before anyone sees it. A change must not open a path around either look.
- **Feedback follows the fourteen teaching rules in `evalkit/rubric/`.** On the colour entrance nothing
  is corrected, ever.
- Where a child's drawing and voice go is written down in [the deployment guide](docs/guides/deployment-versions.md).
  A change that sends either somewhere new must say so there.

## Setting up

Python 3.13 with [uv](https://docs.astral.sh/uv/); the page is plain JavaScript with no bundler.

```bash
uv sync                                  # dependencies from uv.lock into .venv, test tools included
cp .env.example .env                     # fill in the keys you have; .env is never committed
```

## Running the checks

```bash
uv run pytest                            # the Python suite; tests marked `live` spend money and are deselected
node --test "tests/page/*.test.mjs"      # the teacher page's checks
uv run python -m evalkit.signing verify skills   # every Skill folder still matches its signature
```

The maintainers run all of this on the DGX Spark that serves the class, with
`sh deploy/spark/test-on-spark.sh`; you do not need a Spark to contribute.

The teacher's page is generated: edit the numbered fragments in `studio/page/src/`, then rebuild with
`sh studio/page/build.sh`. A hand edit to `studio/page/index.html` is overwritten by the next build.

## How the code is laid out

The [README's project layout](README.md#project-layout) shows where each part of the studio lives, and
[docs/README.md](docs/README.md) is the map of the documents: where the design decisions live and where
the evidence for each claim is kept. A new module goes in the folder of the job it does; a test goes in
the matching folder under `tests/`.

## Conventions

- **A Skill never calls a vendor.** It calls a named slot (`vlm.studio`, `video.animation`, …) and a
  profile in `studio/profiles/` says which model answers it.
- **A claim about model behaviour needs a record in `docs/measured/`.** Without one it is a plan, not a
  result.
- **Ports** are 7000–7700 and end in zero; the rule lives in `studio/server/ports.py` and is tested.
- **Words a teacher or child reads** go through the page's locale table (`studio/page/locales/zh.js`).
  Chinese in Python or JavaScript is allowed only where it is product content, such as prompts.
- **Keep files under 500 lines.** Split by subject before adding to a file that is close.
- **Prose style.** Docstrings say why a thing exists and what it does not promise; tests read as
  sentences. Match the file you are editing.
- **Commit messages** are `<type>: <imperative summary>`, with `feat`, `fix`, `refactor`, `docs`, `test`
  or `chore`.

## Pull requests

- One change per pull request, with tests for new behaviour.
- Say what a teacher would see differently, and attach a screenshot for any change to the page.
- If the change touches a Skill folder, the folder's signature must be renewed by a maintainer; say so in
  the description.

## Reporting

Bugs and ideas: open an issue. A security problem, or anything that could
expose a child's data: follow [SECURITY.md](SECURITY.md) and do not open a public issue.
